# CI

«CI» у сайдбарі (гаряча клавіша Y) — місце, де ви стежите за GitHub Actions проєкту й тримаєте їх зеленими: запуски його репозиторію наживо, те, що заважає перевіркам проходити, і статус CI гілки кожної задачі. Vibe Teamlead нічого не публікує й не хостить; де працює код, вирішуєте ви.

Поки не все готово, нумерований список угорі показує, чого ще бракує: увійти в GitHub, установити GitHub App Vibe Teamlead, налаштувати CI для проєкту. Біля кожного кроку є кнопка; виконані кроки позначено, а коли все готово, список зникає.

У CI три вкладки: **Запуски**, **Готовність CI** і **Налаштування**.

## Запуски

Останні запуски GitHub-репозиторію проєкту перелічено ліворуч. Виберіть один, і праворуч відкриється його граф: джоби workflow, згруповані в етапи за їхніми `needs`. Джоби, які не залежать одне від одного, стоять в одному етапі; ті, що на них чекають, йдуть у наступному.

Статус живий. Вигляд оновлюється кожні 5 секунд, поки щось виконується, і кожні 60 секунд в інший час. Оновлення йде лише поки «CI» відкритий і вікно видиме.

Клацніть джоб, щоб побачити його кроки, які оновлюються, поки він виконується. Його лог, останні 2 000 рядків, з'являється, коли джоб завершиться. GitHub зберігає логи обмежений час, тож для старого запуску може бути написано, що GitHub більше не зберігає його лог; **Повний лог на GitHub** відкриває його там.

Джоб, що запускається кілька разів (матриця, наприклад окремий образ для кожного застосунку, або reusable workflow), — це один блок у графі. Частини його назви, які GitHub підставляє під час запуску (`${{ … }}`), показано як `…`; наведіть на блок, щоб побачити назви його джобів, і клацніть, щоб вибрати, чиї кроки й лог дивитися.

## Що для цього потрібно

- **Вхід у GitHub і встановлений застосунок.** Це два кроки: увійти, потім установити застосунок Vibe Teamlead на GitHub і дати йому репозиторій. Якщо ви не ввійшли, у вигляді є кнопка **Підключити GitHub**; якщо застосунок ще не встановлено, вона просить і про крок установлення.
- **Репозиторій проєкту на GitHub.** Без нього вигляд про це каже і перевіряє знову щохвилини.
- **Схвалені дозволи застосунку.** GitHub App Vibe Teamlead потрібні дозволи на репозиторій: Actions (запуски й логи), Contents (пуш гілок), Workflows (пуш комітів, що змінюють файли workflow), Secrets (секрети CI) і Commit statuses. Коли GitHub просить схвалити нові дозволи, відкрийте https://github.com/settings/installations, виберіть застосунок Vibe Teamlead і прийміть запит. Коли доступу бракує, поряд із повідомленням є кнопка **Керувати доступом на GitHub**.

## Коли щось не так

- **Застосунок не може прочитати Actions репозиторію:** дозволи вище ще не схвалено, або застосунок не має доступу до цього репозиторію. **Керувати доступом на GitHub** відкриває сторінку, де це виправити.
- **GitHub не знаходить цей репозиторій:** репозиторій приватний, а застосунок не має до нього доступу, або його вже нема. Коли застосунок не встановлено на власника репозиторію, **Установити застосунок на GitHub** відкриває сторінку встановлення; інакше **Керувати доступом на GitHub** дає змогу додати репозиторій до застосунку (https://github.com/settings/installations → застосунок Vibe Teamlead → додати репозиторій).
- **Досягнуто ліміту запитів GitHub:** вигляд призупиняється до показаного часу й далі продовжує сам.
- **GitHub не відповідає:** вигляд про це каже й пробує знову. Лог, який не завантажився, теж запитується знову.
- **Origin проєкту не на GitHub:** CI працює лише з репозиторіями GitHub.

## Готовність CI

Вкладка **Готовність CI** (між «Запусками» та «Налаштуваннями») показує, що заважає CI на GitHub Actions проєкту проходити: чи є workflow для проєкту, чи встановлює він на чистому раннері те, що потрібно перевіркам, чи запускає він перевірки проєкту, і останній запуск у main.

**Коли йде перевірка.** Перевірка запускається, коли «CI» відкривають уперше для проєкту без збереженого результату, після мержу в main для проєкту, що його має, і за **Перевірити ще раз**. Це виклик моделі, тож він коштує токенів. Перевірка читає код і приклади env-файлів, але ніколи не значення з файлів `.env` чи ключі. Її модель — **Готовність CI** у Налаштування → Налаштування агентів → моделі функцій (типово Sonnet, низьке мислення).

**Перешкоди стають задачами.** Кожна перешкода в коді чи в workflow CI отримує власну задачу. Задачі потрапляють у **Чергу** й стартують самі в межах ліміту паралельних задач проєкту, як і будь-яка задача в черзі (задачі з черги стартують, поки відкрито дошку задач). Після QA задача зливається сама, навіть коли автомерж проєкту вимкнено. Це стосується лише задач, створених самим CI. Нова перевірка не дублює задачу, що ще відкрита: перевірці повідомляють перешкоди, які вже відомі, і для кожної знайденої проблеми вона каже, чи це одна з них. Коли не каже, перешкода з тією самою назвою або здебільшого з тими самими словами й без нічого, що називає іншу річ, лишається тією самою перешкодою; установлення браузера Playwright і браузера Vitest чи контейнери Postgres і Redis лишаються двома. Поки її задача відкрита, перешкода, яку перевірка цього разу не назвала, зберігає свою задачу й лічильник. Назва відкриває задачу, а перешкода стає виконаною, коли виконано задачу. Перешкода workflow і невдалий запуск у main ніколи не отримують задачу одночасно.

**Workflow.** Workflow GitHub Actions пишеться для цього проєкту. Він установлює на чистому раннері те, що потрібно перевіркам: браузери для Playwright і для юніт-тестів у браузерному режимі, сервіси як контейнери, менеджер пакетів. Гілки задач запускають typecheck і юніт-тести; main запускає все. Після того як workflow потрапляє в main, застосунок стежить за його першим запуском, як за будь-яким запуском у main, і збій стає задачею на виправлення.

**Потрібно від вас** перелічує те, що можете зробити лише ви. Кожен секрет, який читає workflow (`${{ secrets.NAME }}`), а в репозиторії на GitHub його нема, указано тут за назвою; він ніколи не стає задачею, бо агент не може знати значення, а перевірка його ніколи не просить. Секрети йдуть у репозиторій GitHub, тож до налаштування CI біля кожного сказано спершу налаштувати CI. Коли CI налаштовано, біля кожного є **Додати секрет**: введіть значення один раз, і воно збережеться як секрет GitHub Actions, зашифроване для GitHub; воно більше ніколи не показується, не зберігається в застосунку й не потрапляє в репозиторій чи промпт. Секрет зникає зі списку, щойно GitHub його має, без нової перевірки, а повідомлення вгорі вкладки каже, скільки секретів CI ще потрібно. **CI** показує workflow і останній запуск у main. Число на вкладці — скільки перешкод знайшла остання перевірка; воно оновлюється, коли перевірка йде знову, наприклад після мержів. Старий збережений результат усе ще відкривається: усе, що в ньому про хостинг, не показується й ніколи не стає задачею.

**Нічого не заважає.** Коли виправлено останню перешкоду, вкладка каже, що CI ніщо не заважає.

## Невдалий запуск у main

Після пушу в main застосунок до години стежить за запусками цього коміту. Найновіший невдалий запуск workflow у main стає однією термінової задачею на виправлення з логами невдалих джобів. Поки ця задача відкрита, другої нема. Її нема й тоді, коли над цим уже працює інша задача: задача перешкоди workflow, виправлення базової гілки (лише для workflow, що запускає перевірки проєкту) або розпочата задача, у назві чи описі якої названо файл workflow чи workflow як такий («запуск CI», «workflow CI», «CI падає»). Задачі, що ще в «Плануванні», не рахуються. Невдалий запуск розглядається знову під час наступних опитувань і отримує задачу, коли та інша задача закрита, а main усе ще падає. Компроміс: поки така задача відкрита, main може лишатися червоним через причину, яку ця задача не виправляє, доки вона не закриється. Запуски з форків і pull request’ів ігноруються.

**Здаємося.** Коли перешкоду чи падаючий workflow двічі виправляли й вони повернулися, третьої задачі нема: вона переходить у **Потрібно від вас** (із посиланням на запуск), і ви дивитеся на неї самі. Щойно workflow проходить або перевірка більше не знаходить перешкоди, відлік починається знову.

## CI на картках задач

Картка й вікно задачі показують CI її власної гілки. Лише поки задача виконується, на AI-рев'ю, на вашому рев'ю або в помилці:

- **Нічого:** гілку ще не запушено, або CI для проєкту не налаштовано. У вікні задачі тоді є рядок про це з **Налаштувати CI**.
- **CI виконується**, **CI пройшов** або **CI не пройшов.** **CI не пройшов** відкриває CI → «Запуски» на цьому запуску, на логу джоба, що впав.
- **Публічний репозиторій** статусу не отримує: вікно задачі каже, що статус CI потребує приватного репозиторію, і жодну гілку задачі не пушать.

Статус береться із запусків GitHub Actions останнього запушеного коміту гілки. Поки запуск активний, він оновлюється кожні 30 секунд; коли всі його запуски завершилися, застосунок перестає питати, а статус, що не встановився за 10 хвилин після пушу, вважається встановленим, тож пуш, який не запускає жодного запуску, не чекає вічно. Повторний запуск того самого коміту на GitHub не помічається до наступного пушу гілки, який покаже новий результат. Відмовлений пуш не зупиняє агента: вікно задачі пояснює чому, а останній статус лишається.

## Налаштування й секрети

Поки CI для проєкту не налаштовано, «Запуски» й «Налаштування» пропонують **Налаштувати CI**. Налаштування, на вкладці «Налаштування», іде крок за кроком і показує кожен: репозиторій GitHub (приватний створюється, коли в проєкту його нема), пуш у нього головної гілки, потім CI увімкнено. Крок, що зупинився, можна запустити знову за **Спробувати ще раз**; нічого не створюється двічі.

**Потрібно від вас** тут перелічує те, що можете зробити лише ви, кожне зі своєю кнопкою: підключити GitHub (відкриває вікно входу в GitHub), установити застосунок Vibe Teamlead (відкриває GitHub) або зважити, що репозиторій публічний. Вкладка показує репозиторій і чи він публічний, а розділ **Секрети** перелічує секрети GitHub Actions проєкту за назвами з **Додати секрет** і **Замінити**. Значення вводиться в поле пароля й надсилається на GitHub зашифрованим; прочитати його назад не можна.

Проєкт із незвичною конфігурацією git (наприклад, `origin`, заданий через include) не змінюється: налаштування зупиняється й пояснює, що знайшло, тож нічого не перезаписується.

## Пуші на GitHub

Коли CI налаштовано, застосунок пушить на GitHub токеном GitHub App Vibe Teamlead:

- **main** — після кожного мержу в головну гілку проєкту. Останній пуш і чи він вдався видно вгорі вкладки «Налаштування» (для пушів відтоді, як застосунок відкрито). Коли в main на GitHub є коміти, яких нема на цьому Mac, пуш відхиляється: підтягніть їх у проєкт, і наступний мерж запушить.
- **гілка задачі** — після кожної завершеної підзадачі, після кожного раунду виправлень QA і коли задача йде на рев'ю, щоб на ній запускався CI. Гілка, яка вже є на GitHub, не пушиться вдруге. Це відбувається лише коли репозиторій приватний (репозиторій із невідомою видимістю вважається неприватним) і **Automatically Push New Branches** увімкнено і для проєкту, і для задачі.

Пуш ніколи не форсується. У публічний чи невідомий репозиторій не пушать ніколи; застосунок перевіряє знову, не частіше за раз на годину, що репозиторій досі приватний, а коли він уже не приватний, пуші припиняються.
