# Деплой

«Деплой» у сайдбарі (гаряча клавіша Y) показує, що відбувається з кодом проєкту після того, як його запушено: запуски GitHub Actions його репозиторію наживо і те, куди код вийшов у продакшн.

Поки не все готово, нумерований список угорі показує, чого ще бракує: увійти в GitHub, установити GitHub App Vibe Teamlead, підключити Vercel, налаштувати деплой для проєкту. Біля кожного кроку є кнопка; виконані кроки позначено, а коли все готово, список зникає.

## Запуски

Останні запуски GitHub-репозиторію проєкту перелічено ліворуч. Виберіть один, і праворуч відкриється його граф: джоби workflow, згруповані в етапи за їхніми `needs`. Джоби, які не залежать одне від одного, стоять в одному етапі; ті, що на них чекають, йдуть у наступному.

Статус живий. «Деплой» оновлюється кожні 5 секунд, поки щось виконується, і кожні 60 секунд в інший час. Оновлення йде лише поки «Деплой» відкритий і вікно видиме.

Клацніть джоб, щоб побачити його кроки, які оновлюються, поки він виконується. Його лог, останні 2 000 рядків, з'являється, коли джоб завершиться. GitHub зберігає логи обмежений час, тож для старого запуску може бути написано, що GitHub більше не зберігає його лог; **Повний лог на GitHub** відкриває його там.

Джоб, що запускається кілька разів (матриця, наприклад окремий образ для кожного застосунку, або reusable workflow), — це один блок у графі. Частини його назви, які GitHub підставляє під час запуску (`${{ … }}`), показано як `…`; наведіть на блок, щоб побачити назви його джобів, і клацніть, щоб вибрати, чиї кроки й лог дивитися. Блок на етапі **Деплой** не показує тривалості; наведіть на нього або перейдіть до нього клавіатурою, щоб побачити, як давно цей деплой вийшов у продакшн (коли він уже там).

## Деплой і посилання на продакшн

Етап **Деплой** і посилання **Продакшн** беруться з GitHub Deployments, а не з workflow. Хостинг, який звітує в GitHub, наприклад Vercel через інтеграцію з GitHub, з'являється там зі своїм статусом і логом. Іноді Vercel повідомляє лише статус коміту (перевірку **Vercel** на коміті) без деплою: тоді етап **Деплой** береться з цього статусу, з його станом і посиланням на деплой у Vercel. Якщо ніхто не повідомляє про деплої, граф показує лише джоби workflow.

## Що потрібно

- **Вхід у GitHub і встановлений застосунок.** Це два кроки: увійдіть, а потім установіть застосунок Vibe Teamlead на GitHub і надайте йому доступ до репозиторію. Якщо входу немає, у «Деплої» є кнопка **Під'єднати GitHub**; вона просить і про встановлення, якщо застосунок ще не встановлено.
- **Репозиторій проєкту на GitHub.** Без нього «Деплой» про це каже і перевіряє знову щохвилини.
- **Нові дозволи, підтверджені один раз.** Дозволи застосунку в GitHub тепер включають читання Actions і Deployments. GitHub просить підтвердити їх один раз: відкрийте https://github.com/settings/installations, виберіть застосунок Vibe Teamlead і прийміть запит. Коли доступу бракує, «Деплой» показує поруч із повідомленням кнопку **Керувати доступом на GitHub**.

## Коли щось не так

- **Застосунок не може читати Actions репозиторію:** дозволи вище ще не підтверджено, або застосунок не має доступу до цього репозиторію. **Керувати доступом на GitHub** відкриває сторінку, де це виправити.
- **GitHub не знаходить цей репозиторій:** репозиторій приватний і застосунок не має до нього доступу, або його більше немає. Якщо застосунок не встановлено для власника репозиторію, **Установити застосунок на GitHub** відкриває сторінку встановлення; інакше **Керувати доступом на GitHub** дає змогу додати репозиторій до застосунку (https://github.com/settings/installations → застосунок Vibe Teamlead → додайте репозиторій).
- **Ліміт запитів GitHub вичерпано:** «Деплой» робить паузу до часу, який показує, і далі продовжує сам.
- **GitHub не відповідає:** «Деплой» каже про це й пробує ще раз. Лог, який не завантажився, теж запитується знову.

## Акаунт Vercel

Налаштування → Vercel підключає акаунт Vercel, яким «Деплой» налаштовує хостинг. **Підключити Vercel** першого разу завантажує Vercel CLI (близько 180 МБ, перевіряється перед використанням; завантаження, яке хвилину не отримує даних, зупиняється), показує код і відкриває сторінку входу Vercel у браузері; підтвердьте там код. **Скасувати** зупиняє вхід, і нічого не зберігається. Вхід зберігається у власній теці застосунку, а не у вашому Vercel CLI, і поновлюється сам. Можна натомість вставити токен Vercel: він зберігається зашифрованим на цьому Mac і використовується замість входу через браузер. Якщо цей Mac не може його зашифрувати, токен не зберігається (ніколи відкритим текстом): увійдіть через браузер. З уставленим токеном нічого не завантажується, доки ви вперше не натиснете **Додати базу даних** — тоді завантажується Vercel CLI, з прогресом і кнопкою **Скасувати**. **Відключити** прибирає обидва з цього Mac (на Vercel нічого не відкликається).

## Готовність

Вкладка **Готовність** (між Запусками та Середовищем) показує, що стоїть між проєктом і першим деплоєм.

**Коли йде сканування.** Скан запускається, коли «Деплой» уперше відкривається для проєкту без збереженого результату, після злиття в main для проєкту, який його має, і після **Перевірити ще раз**. Це виклик моделі, тож він коштує токенів. Скан читає код і приклади env-файлів, але ніколи не читає значень із файлів `.env` чи ключів. Його модель — **Deploy readiness** у Налаштування → Агенти → моделі функцій (типово Sonnet, низьке мислення).

**Перешкоди стають завданнями.** Кожна перешкода в коді чи в workflow CI отримує окреме завдання. Завдання стають у **Чергу** і стартують самі, коли це дозволяє ліміт паралельних завдань проєкту, як будь-яке завдання в черзі (завдання з черги стартують, поки відкрита дошка завдань). Після QA завдання саме зливається, навіть коли автозлиття проєкту вимкнено. Це стосується лише завдань, які створив сам «Деплой». Нова перевірка не дублює завдання, яке ще відкрите: скан отримує перелік перешкод, які вже відомі, і для кожної знайденої проблеми каже, чи це одна з них. Якщо він цього не каже, перешкода з тим самим заголовком або здебільшого тими самими словами, без слова, що називає іншу річ, лишається тією самою перешкодою; встановлення браузера для Playwright і для Vitest, або контейнер Postgres і Redis, лишаються двома. Поки її завдання відкрите, перешкода, яку скан цього разу не назвав, зберігає своє завдання і свій лік. Заголовок відкриває завдання, а перешкода позначається виконаною, коли виконано завдання. Перешкода у workflow і невдалий запуск у main ніколи не отримують завдань одночасно.

**Workflow.** Workflow GitHub Actions пишеться для цього проєкту. Він встановлює на чистому раннері все, що потрібно перевіркам: браузери для Playwright і для юніт-тестів у браузерному режимі, сервіси, менеджер пакетів. Гілки завдань запускають перевірку типів і юніт-тести; main запускає все; Vercel деплоїть. Після того як workflow потрапив у main, застосунок стежить за його першим запуском, як за будь-яким запуском у main, і збій стає завданням на виправлення.

**Після пушу в main.** Застосунок стежить за запусками цього коміту до години. Найновіший невдалий запуск workflow у main стає одним терміновим завданням на виправлення з логами невдалих jobs. Поки це завдання відкрите, другого не буде. Його не буде й тоді, коли над цим уже працює інше завдання: завдання про перешкоду у workflow, виправлення базової гілки (лише для workflow, що запускає перевірки проєкту) або розпочате завдання, чий заголовок чи опис називає файл workflow або сам workflow («CI run», «CI workflow», «failing CI»). Завдання, що ще в «Плануванні», не враховуються. Невдалий запуск переглядається знову під час наступних опитувань і отримує своє завдання, щойно те інше завдання закрите, а main досі падає. Компроміс: поки таке завдання відкрите, main може лишатися червоним через причину, яку воно не виправляє, доки його не закрито. Запуски з форків і pull request ігноруються.

**Коли застосунок здається.** Якщо перешкоду чи workflow, що падає, виправили двічі, а проблема повернулася, третього завдання не буде: вона переходить у **Потрібно від вас** (з посиланням на запуск), і ви дивитеся на неї самі. Щойно workflow проходить або скан більше не знаходить перешкоду, лік починається знову.

**Що Vercel не може запустити.** Redis (Upstash) і Blob додаються в Середовище → Сервіси. Kafka, споживачі черг і воркери, що працюють постійно, показано як частини, які Vercel не може запустити, без завдання.

**Потрібно від вас** — те, що можете зробити лише ви. Змінні середовища, потрібні розгорнутому застосунку, яких ще немає в проєкті (і ключі сторонніх сервісів, і власні налаштування та секрети застосунку), показано тут поодинці; вони ніколи не стають завданнями, бо агент не може знати значень. Значення зберігаються в проєкті Vercel, тож поки деплой не налаштовано, біля кожної змінної написано, що спершу треба налаштувати деплой. Відсутні змінні не затримують налаштування. Коли деплой налаштовано, біля кожної є **Додати значення**, змінна зникає, щойно вона з'являється у Vercel, а повідомлення вгорі вкладки каже, скільки значень ще потрібно розгорнутому застосунку, щоб він працював. **CI** показує workflow і останній запуск у main. Число на вкладці — скільки перешкод знайшла остання перевірка (частини, які Vercel не може запустити, не враховуються); воно оновлюється, коли перевірка запускається знову, наприклад після злиттів.

**Нічого не заважає.** Коли виправлено останню перешкоду, деплой налаштовується сам. Виняток — акаунт Vercel із командами, де для проєкту ще нічого не обрано: спершу оберіть команду на вкладці «Середовище».

## Попередній перегляд

Попередній перегляд завдання — це збірка Vercel його гілки; воно показується на картці завдання і в його вікні.

**Коли пушаться гілки.** Після кожної завершеної підзадачі, після кожного раунду виправлень QA і коли завдання переходить на рев'ю, застосунок пушить гілку завдання на GitHub із токеном GitHub App Vibe Teamlead, щоб Vercel її зібрав. Гілку, яка вже є на GitHub, повторно не пушить. Це відбувається лише тоді, коли для проєкту налаштовано деплой, репозиторій приватний (репозиторій із невідомою видимістю вважається неприватним), а **Автоматично надсилати нові гілки** увімкнено і для проєкту, і для завдання. Пуш ніколи не примусовий. Відхилений пуш не зупиняє агента: вікно завдання каже, чому, а останнє прев'ю лишається. Попередні перегляди зберігаються після перезапуску застосунку.

**Що показує картка.** Лише поки завдання виконується, на AI-рев'ю, на вашому рев'ю або в помилці:

- **Деплой не налаштовано:** на картці нічого. У вікні завдання є рядок про це з кнопкою **Налаштувати деплой**.
- **Гілку ще не запушено:** нічого.
- **Збирається:** **Перегляд** зі спінером. Відкриває попереднє посилання, якщо воно є.
- **Готово:** **Перегляд ↗**, відкриває посилання (лише https). Наведіть курсор, щоб побачити адресу й час збирання.
- **Зібрано, адреса невідома:** **Перегляд зібрано — відкрити у Vercel**, відкриває сторінку деплою у Vercel, де є посилання на перегляд. Так буває, коли Vercel повідомляє про збірку лише статусом коміту, у якому немає адреси перегляду; застосунок ніколи її не вгадує.
- **Не вдалося:** **Перегляд не вдався**. Відкриває журнал збірки Vercel. Якщо впала перевірка GitHub Actions цього коміту, натомість відкриває «Деплой» → «Запуски» на цьому запуску, на логу джоба, який упав.

Вікно завдання показує те саме: посилання, **Перегляд збирається…** (з попереднім посиланням, якщо воно є) або **Перегляд не вдався** з журналом збірки чи запуском, що впав.

Для публічного репозиторію вікно завдання каже, що для перегляду потрібен приватний репозиторій, і гілка завдання не пушиться взагалі, навіть коли завдання стартує. Застосунок не частіше ніж раз на годину перевіряє, що репозиторій досі приватний; коли він перестав бути приватним, пуші припиняються.

**Звідки береться стан.** З GitHub Deployments для гілки завдання, того самого джерела, що й вкладка «Деплой». Коли для гілки їх немає — зі статусу Vercel для запушеного коміту (якщо проєктів Vercel кілька, перемагає збій, потім той, що ще збирається): виконується — збирається, не вдався — не вдався (з посиланням на Vercel), пройшов — готово, якщо статус дає адресу перегляду, інакше зібрано. Поки триває збірка, він оновлюється кожні 30 секунд, а також щоразу, коли гілку запушено. Готовий, зібраний або невдалий перегляд не запитується знову до наступного пушу.

**Вхід.** Vercel за замовчуванням захищає попередні перегляди: відкривайте посилання, увійшовши у Vercel.

**Перегляд і секрети.** Vercel збирає попередні перегляди з коду агентів зі змінними середовища Preview. Тримайте чутливі ключі (наприклад, бойові платіжні ключі) лише в Production або задайте для Preview окремі тестові значення.

## Середовище: налаштування деплою

У «Деплої» три вкладки: **Запуски**, **Готовність** та **Середовище**. Поки деплой для проєкту не налаштовано, Запуски та Середовище пропонують **Налаштувати деплой**.

Налаштування на вкладці «Середовище» йде крок за кроком і показує кожен: репозиторій GitHub (якщо в проєкту його нема, створюється приватний, і в нього пушиться головна гілка), проєкт Vercel, підключений до цього репозиторію, далі деплой увімкнено: Vercel деплоїть у продакшн після кожного пушу в main. Якщо до цього репозиторію вже підключено проєкт Vercel, оберіть його або створіть новий. Якщо у вашому акаунті Vercel є команди, спершу оберіть, куди йде проєкт: в особистий акаунт чи в команду. Крок, що зупинився, можна запустити знову кнопкою **Спробувати ще раз**; нічого не створюється двічі.

Vercel деплоїть коміт, лише коли може пов'язати його автора з вашим акаунтом GitHub. Якщо в git проєкту не вказано email (тоді git підписує коміти як `you@your-mac.local`), налаштування ставить для цього проєкту вашу службову адресу GitHub (`<id>+<login>@users.noreply.github.com`). Адресу, яку ви вказали самі, не змінює.

**Потрібно від вас** — те, що можете зробити лише ви, кожне зі своєю кнопкою: підключити Vercel (відкриває Налаштування → Vercel) або підключити GitHub (відкриває діалог входу в GitHub), встановити застосунок Vibe Teamlead або дати GitHub-застосунку Vercel доступ до репозиторію (відкриває GitHub), обрати наявний проєкт Vercel для репозиторію чи створити новий, або взяти до відома, що репозиторій публічний.

Після налаштування вкладка показує, що вже є: репозиторій і чи він публічний, проєкт Vercel, адресу продакшну й базу даних. Відтоді після кожного злиття в головну гілку проєкту main пушиться на GitHub, а Vercel його деплоїть; останній пуш і чи він вдався видно вгорі вкладки (для пушів відтоді, як застосунок відкрито). Коли в main на GitHub є коміти, яких немає на цьому Mac, пуш відхиляється: підтягніть їх у проєкт, і наступне злиття запушить main.

Проєкт із незвичною конфігурацією git (наприклад, `origin` задано через include) не змінюється: налаштування зупиняється й пояснює, що знайшло, тож нічого не перезаписується.

## Змінні й база даних

**Додати змінну** зберігає змінну в проєкті Vercel для Production, Preview або обох, а якщо позначити — ще й як секрет GitHub Actions. Значення вводиться в поле пароля й більше ніколи не показується; у списку лише назви, де вони діють і чи вони є також у GitHub. Коли один бік зберіг, а інший — ні, діалог каже, який саме.

**Додати базу даних** додає безкоштовну базу Postgres (Neon) до проєкту Vercel. Першого разу Vercel просить прийняти умови Marketplace для Neon: вкладка показує посилання на правила разом із сайтом, який кожне відкриває, і нічого не приймається, доки ви не натиснете **Прийняти й додати базу даних**. Якщо Vercel потребує кроку, який можна зробити лише в його панелі, вкладка дає туди посилання. З уставленим токеном перше **Додати базу даних** спершу завантажує Vercel CLI (прогрес і **Скасувати** видно на вкладці).

**Сервіси.** Коли перевірка готовності бачить, що проєкту потрібні Redis або Blob, розділ **Сервіси** на вкладці «Середовище» показує їх, кожен із кнопкою **Додати**. Redis надходить із Vercel Marketplace (Upstash), а Blob — власне сховище файлів Vercel; обидва проходять ті самі кроки, що й база даних: умови Marketplace (для Redis) показуються першими й приймаються лише після вашого натискання, завантаження CLI показує прогрес із кнопкою **Скасувати**, а їхні змінні потрапляють у Production і Preview. Сервіси, яких Vercel не може надати, показані з причиною.

**Preview-деплої і база даних.** Змінні бази йдуть у Production і Preview, тож preview-деплої можуть працювати з тією ж базою, що й продакшн, і те, що пише preview, потрапляє у ваші продакшн-дані. Інакше, якщо в інтеграції Neon увімкнено гілки для preview: тоді кожен preview отримує власну копію (гілку бази). Щоб перевірити, відкрийте Vercel → **Storage** → базу → її налаштування і подивіться, чи preview-деплої отримують власну гілку бази; увімкніть це там, якщо хочете тримати preview окремо.
