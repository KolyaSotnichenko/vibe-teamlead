# Агенти і їхні ролі

Кожен агент — це сесія Claude Code зі своїм промптом (`apps/desktop/prompts/`), набором інструментів і своєю моделлю.

| Агент | Роль |
|---|---|
| **Аналітик ТЗ** (brief_analyst) | Читає документ і проєкт, ставить уточнювальні питання (Superpowers brainstorming) і розбиває ТЗ на задачі; відповіді, припущення й відкриті питання показує на кроці перегляду. |
| **Оцінювач складності** | Обирає глибину конвеєра специфікації. |
| **Збирач вимог, дослідник, контекст, discovery** | Готують матеріал для спеки. |
| **Специфікатор** (spec_writer) | Пише `spec.md` з AC. |
| **Критик спеки** | Шукає дірки та суперечності. |
| **Архітектор** | Пише `architecture.md`, ADR і діаграми; рендерить кожну діаграму й виправляє її. |
| **Дизайнер** | Для задачі зі змінами UI: малює wireframe, а потім екрани в дизайн-системі, як HTML у теці спеки задачі (див. «Дизайн перед кодом»). |
| **Агент дизайн-системи** | Витягує дизайн-систему проєкту з коду або проєктує нову за референсами й брифом. |
| **Планувальник** | Пише `implementation_plan.json`: фази, підзадачі, тест-перше, залежності. |
| **Кодер** | Пише код за підзадачами (TDD), комітить, оновлює статус підзадачі; оновлює `RUNNING.md` (як запустити проєкт), коли підзадача змінює, як проєкт встановлюється, налаштовується чи запускається. |
| **QA-рев'юер** | Перевіряє AC, тести, UI (браузер), безпеку і те, що `RUNNING.md` відповідає зміні; пише звіт; відмічає чекбокси спеки. |
| **QA-фіксер** | Виправляє зауваження QA. |
| **UX-рев'юер** | Проходить запущений застосунок у Preview так, як це робить людина, і перелічує те, що заважає людям (див. «Preview»). QA робить те саме рев'ю сторінок, які змінила задача. |
| **Готовність CI** | Читає проєкт і шукає те, що заважає його GitHub Actions CI проходити; перешкоди стають задачами (див. «CI»). |
| **Merge integrator** | Вливає свіжу основну гілку в задачу перед злиттям: розв'язує конфлікти, запускає перевірки проєкту, править те, що зламало злиття. |
| **Генератори commit message / опису PR** | Пишуть повідомлення коміту й текст PR. |
| **PR-рев'юер і спеціалісти** | Рев'ю чужих PR: безпека, якість, логіка, відповідність кодовій базі. |
| **Roadmap, конкурентний аналіз, Ideation, Insights-чат, Changelog** | Утиліти планування й знань. |

## Субагенти

Планувальник, кодер, QA і QA-фіксер можуть доручати частину роботи субагентам-помічникам:

| Субагент | Що робить | Кому доступний |
|---|---|---|
| **Дослідник** (explorer) | Шукає й читає код і повідомляє, де що лежить і як працює. Лише читає. | Планувальник, кодер, QA, QA-фіксер |
| **Запуск тестів** (test runner) | Запускає тести, лінт чи збірку й повідомляє лише про те, що впало. | Кодер, QA, QA-фіксер |
| **Рев'юер** (reviewer) | Перевіряє поточні зміни на відповідність підзадачі чи критеріям приймання. | Кодер, QA-фіксер |

Кожен субагент працює у власному контексті й повертає короткий звіт, тож контекст самого агента лишається на задачі. Ці помічники не змінюють файли: у них немає Write/Edit та інструментів, що змінюють стан збірки. Усе інше вони успадковують від агента: MCP-сервери (CodeGraph, Context7, пошук у пам'яті, браузер у QA), скіли Superpowers, веб. Хуки безпеки (межі шляхів, allowlist команд) діють і для них.

**Власні субагенти агента.** Агент може й сам створити потрібного йому субагента: викликає Agent без типу й сам пише інструкцію (наприклад, «дослідити API цієї бібліотеки» чи «написати тести для окремого модуля»). Це вбудований субагент Claude Code (general-purpose). Він успадковує всі інструменти агента, зокрема редагування, тому агента просять давати йому файли, яких не торкаються інші субагенти, і перевіряти його роботу. Підзадачі плану, як і раніше, виконуються по одній.

Поки субагент працює, картка задачі показує, скільки їх працює (наведіть, щоб побачити імена), а в **Логах** під рядком субагента з відступом видно його власні виклики інструментів.

У **«Налаштування → Агенти → Субагенти»** їх можна вимкнути або вибрати модель — і для помічників, і для власних субагентів агента. За замовчуванням вони працюють на моделі самого агента. Для пошуку й тестів зазвичай досить дешевшої моделі, але її має обслуговувати ваш endpoint (наприклад, ваш шлюз).

## Довгий вивід команд

Кожен хід агента заново надсилає все, що було до нього, тож тестовий прогін на тисячі рядків оплачувався б знову на кожному наступному ході. Коли агент запускає тести, збірку, перевірку типів, встановлення залежностей чи лінтер, увесь вивід зберігається в лог у теці задачі (`.vibe-teamlead/specs/<задача>/logs/`), а якщо він довгий, агент отримує коротку версію: код виходу, якщо команда впала — рядки, схожі на помилки, з кількома рядками довкола, останні рядки і шлях до логу, який він читає, коли потрібно більше. Короткий вивід і команди, які агент фільтрує сам (через `|`, `>` чи у фоні), лишаються як є. Одна труба забирається: `| tail -N` чи `| head -N` на такій команді. Вона ховає код виходу і рядки з помилками, і в реальних сесіях агент після неї у чверті випадків запускав той самий набір тестів удруге; коротка версія застосунку має і те, і те. Власні перевірки застосунку перед QA і після злиття це не зачіпає.

## Довгі сесії

Дизайнер, кодер і QA-фіксер стискають розмову, коли вона сягає приблизно 170 тис. токенів (а не біля вікна моделі в 1 млн): Claude Code замінює історію підсумком, і підсумок зберігає те, що потрібно ролі, — для кодера підзадачу, її тест, що падає, і його файл, змінені файли і що лишилось; для дизайнера готові й решту фреймів, ваші коментарі дослівно і рішення дизайн-системи; для QA-фіксера виправлені й решту проблем. Кожне стискання перебудовує кеш промпту, тож поріг навмисно високий; коли це стається, у журналі задачі з'являється рядок. Інші агенти працюють із типовим порогом Claude Code.
