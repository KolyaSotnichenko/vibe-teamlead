# CI

CI, in the sidebar (shortcut Y), is where you watch your project's GitHub Actions and keep them green: the runs of its repository, live, what stops the checks from passing, and the CI status of every task's branch. Vibe Teamlead doesn't publish or host anything; where the code runs is up to you.

Until everything is ready, a numbered list on top says what is still missing: sign in to GitHub, install the Vibe Teamlead GitHub App, set up CI for the project. Each step has its button; done steps are ticked, and the list disappears once all are done.

CI has three tabs: **Runs**, **CI readiness** and **Setup**.

## Runs

The latest runs of the project's GitHub repository are listed on the left. Pick one and its graph opens on the right: the workflow's jobs, grouped into stages by their `needs`. Jobs that don't depend on each other sit in the same stage; the ones that wait for them come in the next.

Status is live. The view refreshes every 5 seconds while something is running and every 60 seconds otherwise. It refreshes only while CI is open and the window is visible.

Click a job to see its steps, updated while it runs. Its log, the last 2 000 lines, appears once the job finishes. GitHub keeps logs for a limited time, so an old run may say that GitHub no longer keeps its log; **Full log on GitHub** opens it there.

A job that runs several times (a matrix, such as one image per app, or a reusable workflow) is one box in the graph. Parts of its name that GitHub fills in while it runs (`${{ … }}`) show as `…`; hover the box to see the names of its jobs, and click it to pick which one's steps and log to see.

## What it needs

- **GitHub signed in, and the app installed.** These are two steps: sign in, then install the Vibe Teamlead app on GitHub and give it the repository. When you aren't signed in, the view has a **Connect GitHub** button; it asks for the install step too when the app isn't installed yet.
- **The project's repository on GitHub.** Without one, the view says so, and checks again every minute.
- **The app's permissions approved.** The Vibe Teamlead GitHub App needs repository permissions for Actions (runs and logs), Contents (pushing branches), Workflows (pushing commits that change workflow files), Secrets (CI secrets) and Commit statuses. When GitHub asks you to approve new permissions, open https://github.com/settings/installations, choose the Vibe Teamlead app and accept the request. When access is missing, the view shows a **Manage access on GitHub** button next to its message.

## When something is wrong

- **The app can't read the repository's Actions:** the permissions above aren't approved yet, or the app has no access to this repository. **Manage access on GitHub** opens the page to fix it.
- **GitHub can't find this repository:** the repository is private and the app has no access to it, or it no longer exists. When the app isn't installed on the repository's owner, **Install the app on GitHub** opens the install page; otherwise **Manage access on GitHub** lets you add the repository to the app (https://github.com/settings/installations → the Vibe Teamlead app → add the repository).
- **GitHub's rate limit is reached:** the view pauses until the time it shows and continues by itself.
- **GitHub isn't responding:** the view says so and tries again. A log that didn't load is asked for again too.
- **The project's origin is not on GitHub:** CI works with GitHub repositories only.

## CI readiness

The **CI readiness** tab (between Runs and Setup) shows what keeps the project's GitHub Actions CI from passing: a workflow exists for the project, it installs on a clean runner what the checks need, it runs the project's checks, and the last run on main.

**When it scans.** The scan runs the first time CI opens for a project with no saved result, after a merge into main for a project that has one, and on **Check again**. It is a model call, so it costs tokens. The scan reads code and example env files, never the values in `.env` files or keys. Its model is **CI readiness** in Settings → Agent Settings → feature models (default Sonnet, low thinking).

**Blockers become tasks.** Each blocker in the code or in the CI workflow gets its own task. The tasks go into the **Queue** and start by themselves as the project's parallel-task limit allows, like any queued task (queued tasks start while the task board is open). After QA, a task merges by itself, even when the project's auto-merge is off. This applies only to tasks CI itself created. A new check doesn't duplicate a task that is still open: the scan is told the blockers it already knows, and says for each problem it finds whether it is one of them. When it doesn't say, a blocker with the same title, or mostly the same words and nothing that names a different thing, stays the same blocker; a Playwright browser install and a Vitest one, or a Postgres and a Redis container, stay two. While its task is open, a blocker the scan doesn't name this time keeps its task and its count. The title opens the task, and the blocker turns done when the task is. A workflow blocker and a failed run on main never get a task at the same time.

**The workflow.** The GitHub Actions workflow is written for this project. It installs on a clean runner what the checks need: browsers for Playwright and for unit tests in browser mode, services as containers, the package manager. Task branches run typecheck and unit tests; main runs everything. After the workflow lands on main, the app follows its first run like any run on main, and a failure becomes a fix task.

**Needed from you** lists what only you can do. Each secret a workflow reads (`${{ secrets.NAME }}`) that the repository doesn't have on GitHub is listed here by name; it never becomes a task, since an agent can't know the value, and the check never asks for one. Secrets go to the GitHub repository, so before CI is set up each one says to set up CI first. Once it is set up, each one has **Add secret**: type the value once and it is saved as a GitHub Actions secret, encrypted for GitHub; it is never shown again, never kept in the app and never written to the repository or a prompt. A secret disappears as soon as GitHub has it, without a new check, and a notice at the top of the tab says how many secrets CI still needs. **CI** shows the workflow and the last run on main. The number on the tab is how many blockers the last check found; it updates when the check runs again, for example after merges. An old saved result still opens: whatever it says about hosting is not shown and never becomes a task.

**Nothing blocks.** When the last blocker is fixed, the tab says that nothing blocks CI.

## A failed run on main

After a push to main the app follows that commit's runs for up to an hour. The newest failed run of a workflow on main becomes one urgent fix task, with the logs of the failed jobs. While that task is open there is no second one. There is none either while another task is already working on it: a workflow blocker task, a base-branch fix (only for the workflow that runs the project's checks), or a started task whose title or description names the workflow's file or the workflow as such ("CI run", "CI workflow", "failing CI"). Tasks still in Planning don't count. The failed run is looked at again on later polls, and gets its task once that other task is closed and main is still failing. The trade-off: while such a task is open, main can stay red for a reason that task doesn't fix, until it closes. Runs from forks and pull requests are ignored.

**Giving up.** When a blocker or a failing workflow has been fixed twice and comes back, there is no third task: it moves to **Needed from you** (with a link to the run), and you look at it yourself. Once the workflow passes or the scan no longer finds the blocker, the count starts again.

## CI on task cards

A task's card and window show the CI of its own branch. Only while the task is in progress, in AI review, in human review or in error:

- **Nothing:** the branch hasn't been pushed yet, or CI isn't set up for the project. The task window then has a line saying so, with **Set up CI**.
- **CI running**, **CI passed** or **CI failed.** **CI failed** opens CI → Runs on that run, at the log of the job that failed.
- **A public repository** gets no status: the task window says CI status needs a private repository, and no task branch is pushed at all.

The status comes from GitHub Actions' runs of the branch's latest pushed commit. While a run is active it refreshes every 30 seconds; once all its runs have finished it stops asking, and a status that hasn't settled 10 minutes after the push is treated as settled, so a push that starts no run doesn't wait forever. A re-run of the same commit on GitHub isn't noticed until the next push of the branch, which shows the new result. A refused push doesn't stop the agent: the task window says why, and the last status stays.

## Setup and secrets

Until CI is set up for the project, Runs and Setup offer **Set up CI**. Setup, on the Setup tab, goes step by step and shows each one: the GitHub repository (a private one is created when the project has none), the main branch pushed to it, then CI is on. A step that stopped can be run again with **Try again**; nothing is created twice.

**Needed from you** here lists what only you can do, each with its button: connect GitHub (opens the GitHub sign-in dialog), install the Vibe Teamlead app (opens GitHub), or note that the repository is public. The tab shows the repository and whether it is public, and the **Secrets** section lists the project's GitHub Actions secrets by name, with **Add a secret** and **Replace**. A value is typed into a password field and sent to GitHub encrypted; it can't be read back.

A project whose git configuration is unusual (for example, `origin` defined through an include) is not changed: setup stops and explains what it found, so nothing is overwritten.

## Pushes to GitHub

Once CI is set up, the app pushes to GitHub with the Vibe Teamlead GitHub App's token:

- **main**, after every merge into the project's main branch. The last push and whether it worked show at the top of the Setup tab (for pushes since the app was opened). When GitHub's main has commits this Mac doesn't have, the push is refused: pull them into the project, and the next merge pushes.
- **a task's branch**, after each finished subtask, after each round of QA fixes and when the task goes to review, so CI runs on it. A branch GitHub already has is not pushed again. This happens only when the repository is private (a repository whose visibility is unknown counts as not private) and **Automatically Push New Branches** is on for both the project and the task.

A push is never forced. A public or unknown repository is never pushed to; the app checks again, at most once an hour, that a repository is still private, and when it is no longer private, pushes stop.
